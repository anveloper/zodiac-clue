## 1. 확정된 결함 (실코드 검수로 확인)

### 1.1 봇이 사람보다 더 안다 — **공정성·문서 신뢰도 동시 리스크**
- `clue-room.ts`의 `revealed`는 **룸 전역 Set**. 반증 카드가 여기 쌓이고 **모든 봇**이 후보 소거에 쓴다. 사람은 자기에게 보인 카드만 안다.
- 덱 18장·비정답 15장 기준 라운드당 봇 5명이 각 1장 노출 → **3~4라운드면 봇 지식 수렴**. 사람의 실제 행동 턴은 3~4번뿐.
- **AI 기술문서(제출물 ④)에 "공유 공개카드(revealed)"로 명시**돼 있어 심사자가 발견하기 쉽다 → "AI가 치트한다"로 읽힐 유일한 지점.
- 조치: `revealed`를 **공통 단서 전용**으로 축소, 봇별 `seen`(자기 손패+자기에게 보인 카드+공통단서)로 분리. 수렴 보전은 **공개 정보만 쓰는 추론**으로 대체 — "패스한 사람은 그 3장을 안 가짐"(`notHolds`)은 사람도 로그로 도달 가능하므로 비대칭이 아니다.
- 무한 지연 방지: 총 제안 상한(예 40) 초과 시 결정론적으로 공통 단서 1장 추가 공개.

### 1.2 "패스"가 로그에 없다 — 사람 쪽 정보 결손
- `doSuggestion`은 첫 매치에서 `🛡 X 반증`만 브로드캐스트하고 return. **반증 못 한 앞 순서 플레이어들이 로그에 남지 않는다.**
- 정통 클루에서 "누가 못 냈는가"는 카드 내용보다 중요한 공개 정보. 지금은 턴 스트립과 대조해 머릿속 역산이 필요.
- 조치: `suggestLog { sid, by, suspect, weapon, room, passed[], disprovedBy }` 브로드캐스트 + **제안 기록표 패널**(행=제안, 열=6인, 셀=`·`패스/`🛡`반증/나에게 보인 카드). 전부 공개 데이터만 사용 → 진실값 누출 0.
- `onMessage("disprove")`에 증거노트 자동 `cleared` 기록 추가 — 현재 **부수 기능인 `peek`(계략)만 자동 기록되고 주 정보원인 반증은 로그 한 줄로 끝난다**(역전 상태).

### 1.3 심사축 1위(AI)가 화면에 없다
- LLM 기여는 `broadcast("say", {id, from, text})` 한 줄. **LLM인지 캐시인지 규칙 폴백인지, 몇 ms 걸렸는지 아무도 모른다.**
- 조치: `narrate()` 반환을 `{ text, source: "llm"|"cache"|"fallback", ms, model }`로 확장 → `speak()`가 메타 동봉 브로드캐스트 → **AI 디렉터 패널**(우측, 기본 접힘, `?ai=1`이면 펼침)에 `LLM n · 캐시 n · 폴백 n · 평균 Xs`와 최근 발화 로그. 로그 배지 `✨`(llm)/`♻`(cache)/`⚙`(fallback).
- **경계 확인**: 추가 필드는 전부 "문장이 어느 경로로 왔는가" 메타데이터이며 게임 상태가 아니다. 진실값 경계 불변.
- 말풍선은 3개 렌더러가 **이미 동일한 `showBubble(id, text)` 계약** → 배지를 문자열 접두로 넣으면 4뷰 자동 대응.

### 1.4 NPC 페이싱이 필수 제출물(영상)을 막는다
- 봇 1턴 = `npcDelay()` + `BOT_ACT_GAP`(1300) + `SPEAK_HOLD`(2400). 기본값 기준 **봇 5명 = 내 턴 사이 33.5초**, 사람이 20초 숙고하면 상한에 걸려 **53.5초**.
- EMA 결합이 역방향: **오래 고민하는 플레이어를 가장 심하게 벌준다.**
- 조치: 규약("사용자 평균의 절반")은 유지하되 **라운드 예산 상한** `min(현재값, 12000 / 남은 봇 수)` 도입. `SPEAK_HOLD` 2400→1400, 직전 타겟과 같은 방이면 카메라 팬 생략·봇→봇이면 `CAM_SWITCH_DELAY` 900→400. `[⏩ 빠르게]` 토글(촬영용).
- **`TYPE_MS`(55ms 타자기)는 건드리지 않는다** — NPC 대사가 AI 활용의 유일한 가시적 증거다.
- ⚠️ 이 변경은 `CLAUDE.md`·AI 기술문서의 "NPC 딜레이 = 평균의 절반" 규약 문구를 바꾼다 → **코드와 문서를 같은 커밋 묶음으로** 처리해야 심사 시 불일치가 없다.

### 1.5 첫 60초에 규칙을 이해할 방법이 없다
- 튜토리얼·도움말 오버레이 **0건**. 제공되는 것은 로그 1줄과 하단 키 안내뿐.
- `내 단서 패: 잡채, 서재, 뱀 무녀` — **"내 카드는 정답이 아니다"**라는 추리의 출발점이 화면 어디에도 없다.
- 제안 모달이 `needRoom=false`라 **3요소 중 장소를 안 보여준 채 확정**시킨다(서버가 `player.room`에서 조용히 가져감).
- 비활성 사유 안내(`addLog("방 안에서만…")`)는 **disabled 버튼이라 클릭 이벤트가 안 떠 영원히 실행되지 않는 죽은 코드**다.
- 조치: 목표 카드 3줄 오버레이(1회, `?` 재열람, `?demo=1` 스킵) · 손패 라벨에 "이 3장은 정답이 아님" 명시 · 제안 모달에 `장소: <현재 방> (고정)` 읽기전용 행 · 버튼 4종 동적 `title` + 턴 배너 부제 · (P1) 도달 가능 칸 하이라이트(`reachable()`를 `packages/shared`에 1개만 두고 4뷰 공유, **방은 통째로 칠할 것** — 방 안 이동은 무료라 부분 채색은 오해를 부른다).

### 1.6 심사자 진입 장벽
- 랜딩 → 방 만들기 → 대기실 → 캐릭터 선택 → 시작, **4단계**. 계정도 친구도 없는 심사자에게 요건 ①의 "플레이 가능"은 사실상 이 통과율이다.
- 조치: `[혼자 바로 시작 (NPC 5명)]` 버튼 + `?solo=1` 딥링크. **서버 변경 0** — 기존 `create`→`character`→`start` 메시지 3개 조합.

## 2. 4뷰 대응 디자인 (제약 1 준수)

### 2.1 뷰 전환이 "개발 진화"를 전달하지 못한다
- 전달 경로가 좌하단 버튼 라벨 하나뿐 → 심사자에겐 **그래픽 품질 옵션**으로 읽힌다. 왜 항상 뷰1에서 시작하는지도 설명이 없다.
- 조치: `Stage` 타입에 `date·oneLine·tech·commit` 추가(**실제 커밋 해시**가 "개발 과정"이라는 주장의 증거성) → 전환 시 1.1초 인터스티셜(`#diceOverlay` 패턴 복제) + 드롭다운을 **연표**로(날짜·한 줄 설명·`에셋 0`/`에셋 44` 배지).
- 인터스티셜 문구는 자랑이 아니라 **기술 선택의 이유**로("에셋이 0인 상태로 규칙부터 검증했다") — "게임성 부족의 우회"로 읽히는 것을 방어.
- **뷰별 틴트만 다르게**: 뷰1 `#2a2118`(복도색·각진 테두리) / 뷰2 `#1c1712`(CSS perspective 기울임) / 뷰3 동일 틴트+금색 광채 / 뷰4 `#5b8c4a`(grass1·3px 계단 픽셀 보더).

### 2.2 소환이 시각적으로 존재하지 않는다
- 서버는 `target.x/y`만 바꾼다 → 클라는 일반 이동과 구분 못 해 **110ms tween**. 뷰2·3은 장물이 **보간 없이 매 프레임 스냅**(사실상 버그).
- 조치: `fx/fx-bus.ts` — 상태 델타로 판정(체비셰프 2칸 이상 점프 = `warp`), `FxRenderer` 계약(`warp/lootWarp/focusRoom/pulseCell`)을 3개 렌더러가 구현. 카메라 포커스는 뷰1에 구현하면 **뷰4는 카메라 미러링이라 자동 상속**, 뷰2·3만 별도.
- 게이팅: 카메라 포커스는 **내 턴이거나 내가 지목당했을 때만**, 나머지는 배너+펄스만(NPC 6인이 매 턴 제안하므로 과하면 화면이 계속 흔들린다).

| FX | 뷰1 | 뷰2 | 뷰3 | 뷰4 |
|---|---|---|---|---|
| 소환 | `Arc` 잔상 링 3겹 + 금색 사각 펄스, tween 110→420 `Back.easeOut` | `RingGeometry` 펄스 + y축 포물선 호 이동 | 뷰2 + 도착 시 `PointLight` 0.4초 | **사각 프레임 3겹** 확대(도트 문법) + 4방향 화살표 도트 |
| 공통 | 중앙 상단 `#fxBanner` "🐍 뱀이 서재로 불려왔다" 1.2초 — diceOverlay와 동일 레이어 패턴이라 4뷰 공통 보장 | | | |

### 2.3 뷰4가 뷰1보다 정보량이 적다 (진화 서사에 정면 위배)
- 십이지 12종을 **색 6개 순환**으로만 구분, 장물 6종은 **전부 동일한 상자**, 계략 NPC는 **회색 크리터·마크 없음**.
- 조치(전부 코드 생성, 외부 에셋 0 = 뷰4 정체성 유지): `pixel-glyphs.ts` — 귀 4형 × 볏 2형 × 꼬리 3형 × 색 6종으로 12종 구분 / `LOOT_DOTS` 8×8 문자열 6벌을 `generateTexture` / 계략 NPC는 **실루엣은 십이지대로, 색만 회색** + 머리 위 3×3 카드 마크.
- 축소판(1~2h): 머리 위 3×3 도트 문장 배지 12종 + 장물 스탬프 6종만 → 정보 결손의 8할 해소.
- **근거**: 제약 1을 "동일 정보가 4뷰에서 동등하게 읽히는가"로 해석하면 뷰1·2·3은 이미 충족이고 뷰4만 미달이다. 뷰4를 끌어올리는 것이 곧 4뷰 대응이며, 뷰1~3에 손대면 오히려 균일성이 깨진다.

### 2.4 뷰3가 "에셋 대기"가 아니라 역효과 상태
- `public/assets/**` **44/44 전부가 우상단에 `PLACEHOLDER` 배지를 그려 넣은 SVG**이고 내용물도 결국 같은 이모지. → 뷰2→뷰3 전환이 **"이모지가 원판에 갇히고 도장이 찍히는" 역방향 연출**이다.
- 조치 1 (**10분·최고 ROI**): `scripts/gen-placeholder-assets.mjs`의 배지 블록 제거 후 44개 재생성.
- 조치 2 (P1): 뷰3의 차별점을 **텍스처 → 렌더 품질**로 재정의. 현재 조명은 Ambient 0.85 + Directional 0.6뿐(그림자·포그 없음). `setAssets(true)`일 때만 **발밑 접지 데칼**(빌보드라 실그림자가 안 맞음 → 비용·품질 모두 유리) + `THREE.Fog`(42° 원근의 깊이가 처음 읽힌다) + 문기둥 `emissive` 등불 + `CanvasTexture` 야간 배경.
- PNG 아트 도착 시 같은 경로 덮어쓰기만으로 자동 승격(기존 `assetSprite` 폴백 구조 유지).
- ⚠️ 뷰3 정의 변경은 `docs/plans/active/12-view-evolution-stages.md`의 단계 표와 어긋난다 → 문서 동기화 필수.

### 2.5 뷰 간 표기 계약 부재 (뷰5 추가 시 어긋남이 5개로 늘어남)
- 실측된 불일치: **뷰2·3 탈락 표현이 face 스프라이트 알파만 바꾸고 disc·ring·이름표는 그대로** → 탈락자가 살아있는 것처럼 보인다(명백한 버그). 뷰4 말풍선은 **타자기 없음·3200ms**(다른 뷰는 55ms·2600ms). `CAM_SWITCH_DELAY 900`이 두 파일에 중복 정의.
- 조치: `view-consts.ts`(TYPE_MS·BUBBLE_HOLD_MS·WARP_MS·ELIM_ALPHA·CAM_SWITCH_DELAY·MOVE_TWEEN_MS) + `view-contract.ts`(`setCurrent/setElim/warp/lootWarp/bubble/identity`)를 3개 렌더러가 `implements` → **타입 시스템이 4칸 채우기를 강제**.
- **계약은 *정보*만 강제하고 *표현*은 자유로 둔다** — 과하게 조이면 "진화"가 아니라 "같은 게임의 스킨 4개"가 된다.

## 3. 제출물 ② 영상 — 촬영이 아니라 설계
5종 중 **유일한 미제작 필수 항목**(누락 시 심사 제외)이고 심사자가 **끝까지 보는 유일한 산출물**이다. 현재 페이싱으로는 45초 창에 "복도 걷는 장면"만 담기기 쉽고, **"실제 플레이 화면만·AI합성 금지"** 조항 때문에 편집으로 메울 수 없다.

콘티(55초 목표) → `docs/submission/20260728-video-storyboard.{md,html}`로 별도 작성:

| 구간 | 내용 |
|---|---|
| 0-4s | 랜딩 → `[혼자 바로 시작]` → 즉시 진입. 자막 "설치·로그인 없이 즉시 플레이" |
| 4-10s | 2d6 → 방 진입 → `[제안]` → 반증 로그 |
| 10-22s | NPC 대사 말풍선 2개(성격 다른 캐릭터) + AI 디렉터 패널에 `[LLM 0.9s]` 배지가 찍히는 순간. 자막 "결정=규칙엔진 / 대사=LLM" |
| 22-30s | `[계략]` → 귓속말 + `peek` 로그 + 증거노트 자동 제외 체크 |
| 30-42s | **뷰1→2→3→4 4연속 전환.** 자막 "개발 진화 과정을 게임 기능으로" |
| 42-55s | 고발 성공 → 결과 오버레이 → AI 누적 카운터 클로즈업 |

- 촬영 보조는 **표시 계층만**(`?ai=1` 패널 펼침, `?rec=1` 폰트·패널 폭 확대). **주사위·정답·NPC 판정은 절대 손대지 않는다** — 요건 위반이며, 이 경계를 콘티에 명시하는 것 자체가 성실성 증거다.
- **안전 테이크 우선**: 08-03까지 선행 개선이 안 끝나면 현 상태로 먼저 1테이크 녹화·업로드해 요건 충족을 확보하고 이후 재촬영한다.

### 7.5.1 🔴 사람만 "제안한 턴에 고발할 수 없다" (P0 · 0.5h)
`handleSuggest`는 반증 직후 **무조건 `advanceTurn()`** → 사람은 봇 5턴 뒤에야 고발 가능. 반면 봇은 `SPEAK_HOLD` 타이머 안에서 **같은 턴에 고발**한다.
이 비대칭만으로 승률 7.3%→3.9%(사람 승리의 47% 강탈). **판의 10.3%에서 사람이 정답을 확정하고도 자기 턴이 오기 전에 진다.**
- 조치: `advanceTurn()` 제거 → `stepsLeft=0` + `suggestedTurn` 잠금 + `client.send("canAccuse")` → `[고발]`/`[턴 종료]` 선택. 30초 자동 종료 타이머. 서버 ~15줄 + 클라 ~10줄.

### 7.5.2 🟠 같은 방에서 무한 제안 가능 — 보드가 장식이다 (P0- · 2h)
재진입 추적 변수가 코드에 **없다**(정통 클루의 "방에 들어온 턴에 1회"가 통째로 누락). 최적 플레이 = 방 하나에 눌러앉아 매 턴 같은 방 제안.
실측 **사람이 판당 방문하는 방 2.1개 / 9개**, 제안의 27~35%가 직전 턴과 같은 방 → **2d6·9개 방·비밀통로 3쌍이 사실상 무의미**. 통로는 더 심각(`handlePassage`가 턴을 유지해 매 턴 제안 루프 가능).
- 조치: `suggestedIn: Map<playerId, room>`으로 같은 방 재제안 차단(봇 경로에도 동일 적용), 방을 벗어나면 해제. 도입 시 방문 방 3.3→**4.7개**.

### 7.5.3 🟡 봇은 수학적으로 오답 고발이 불가능하다 (P2 · 1.5h)
`eff()`가 빼는 것은 전부 비정답이라 **정답은 항상 후보에 남는다** → 봇 고발은 100% 정답, **봇 탈락 판 0.0%**. 탈락 위험은 사람만 진다.
→ §2.5의 "뷰2·3 탈락 알파 버그"는 **솔로에서 절대 발현되지 않는다**(봇이 안 죽으니까).
- 조치: `BOT_NERVE[suspect]` 페르소나 상수 + 시드 RNG로 `combos<=6`일 때 확률적 도박 고발(결정론 유지 → 진실값 규약 불변). 승률 영향 ±1%p, **봇 탈락 판 0%→4~7%**. 호랑이는 성급히 고발하고 양 목동은 안 한다 → **"페르소나가 대사뿐 아니라 의사결정에도 반영된다"**가 제출물 ④의 강한 근거가 된다.

## 7.7 🟠 `?ai=1` 게이팅은 문제를 재생산한다
§1.3은 문제를 "AI가 화면에 안 보임"이라 진단해놓고 해결책을 **"쿼리 파라미터를 붙여야 보이는 접힌 패널"**로 설계했다. 심사자는 파라미터 없는 URL로 들어온다.

## 7.8 🟠 `rightInset()` null 가드 부재 — 패널을 숨기면 카메라가 붕괴한다 (P0 · 0.5h)
`game-scene.ts`/`iso-view.ts`의 inset 계산이 `window.innerWidth - rect.left`인데, 패널이 `display:none`이거나 하단 시트가 되면 `rect.left===0` → **inset = 화면 전체 폭** → 카메라가 절반만큼 어긋나 내 캐릭터가 화면 밖으로 밀려난다.
- 조치: `if (!el || el.offsetParent === null || rect.width === 0) return {right:0, bottom:0}` + `hudInset(): {right, bottom}`로 승격. **§1.2·§1.3 착수 전 선행 조건.**
- 부수: 반응형 블록이 `.hud-evi`/`.hud-log`를 타깃하는데 **DOM에 그 클래스가 없다**(우측 컬럼이 `.rp-col/.rp-panel`로 재구현됨) → **현재 우측 패널 반응형 CSS는 100% 죽은 코드**. 375px 폰에서 260px 컬럼이 화면의 69%를 덮는다.

## 7.11 🟡 캐릭터 색이 비결정론적이고 HUD와 끊겨 있다
`PLAYER_COLORS`가 **3파일에 6색씩 중복** 정의되고 배정이 `ids.indexOf(id) % 6`(= **접속 순서**)이다 → 같은 캐릭터가 판마다 다른 색, 봇 충원·재접속으로 **판 도중에도 색이 바뀔 수 있다**. 그런데 **HUD는 색을 전혀 쓰지 않는다**(턴 스트립·증거노트·제안 모달 전부 이모지/텍스트) → 색이 아무 정보도 전달하지 않는다.
- 뷰4에서 치명적: `makeCritter`가 12캐릭터 **동일 실루엣**이라 유일한 식별자가 색인데, 그 색이 판마다 바뀐다.
- 색맹: 6색 중 라임·그린·레드가 2형 색각에서 수렴 → 최대 3명 구분 불가.
- 조치: `packages/shared/src/cards.ts`에 **`ZODIAC_COLOR` 12색**(색상 4계열 × 명도 3단, 회색조 명도차 ≥18% 검증 스크립트) → 3개 렌더러 로컬 배열 삭제. 이름표 좌측 3px 색 스트라이프로 **색과 이름을 같은 픽셀에**. `.ti-chip`에 `inset 0 -3px 0 <색>` + 15px→18px + 이름 첫 글자 병기. `?cvd=1`은 토큰 하단 1~12 도트.
- **§2.3(뷰4 실루엣)보다 먼저** 넣어야 `makeCritter` 시그니처를 두 번 고치지 않는다.

## 7.16 🟡 상류 근거와의 논리 단절
- **"load-bearing AI" 용어가 뒤집혀 있다.** 상류 정의는 "**AI 없으면 게임이 성립 안 되는** 설계여야 감점 안 됨(껍데기 AI ❌)"인데, ④는 "**load-bearing AI = 표현 전용**"이라 쓰고 "LLM 장애와 무관하게 게임은 정상"이라고 **자기 선언**한다. 7.1에서 **실제로 제거된 채 라이브 중임이 실측**됐으므로 심사자가 5초 만에 검증할 수 있다.
  → 제목을 **"이중 계층: 결정론적 진실 계층 + LLM 표현 계층"**으로 바꾸고 "왜 판정에서 LLM을 배제했는가"를 **설계 판단으로 논증**(환각·재현성·무료티어·치트 방지). 상류가 요구한 프레이밍은 버리는 게 아니라 **이동**시킨다 — "AI를 어떻게 게임에 넣었나" → **"AI를 어떻게 지휘·검수했나"**(§4가 이미 옳게 짚은 방향, 본행사 산출물 요구와 직결).
- **07-18 확정 차별점(자유 심문·거짓말/뇌물 축)이 미구현**이다. D-14에 신규 구현은 §6.2와 같은 이유로 기각하되, **④에서 "본행사 로드맵"으로 명시적으로 계승**할 것: "자유 심문은 진실값 경계를 LLM에 넘기므로, 사전과제에서 결정론 경계를 먼저 확립하고 본행사에서 검증 프로토콜과 함께 얹는다." 아무 말도 안 하면 **"차별점을 약속하고 안 만든 팀"**과 구분되지 않는다.
- ③에 "왜 이 게임인가" 6줄 추가(장르=소규모 퍼즐 추리, NHN 웹보드/캐주얼 포트폴리오 정합성, 십이지 테마 접근성). 현재 ③은 규칙설명서일 뿐 기획서가 아니다.
- ⚠️ **"심사축 1위(AI)"·"그래픽은 채점 항목이 아니다"는 저장소에 출처가 없다.** 공고 원문이 repo에 없다 → `docs/planning/`에 **공고 원문을 넣고**(30분), 그 전까지 이 우선순위는 **잠정**으로 표기.

# 8. 멀티플레이·재접속 (3차 검수)

> §1~7은 **1인 플레이(사람1+봇5)** 기준이었다. 여러 사람이 함께 하면 판이 깨진다.

## 8.1 🔴 이탈자의 손패가 증발해 "유령 카드"를 만든다 — 진실값이 깨진다 (P0 · 1.5h)
`removePlayer()`는 `players`와 `hands`에서 지우지만 **`turnOrder`에서는 지우지 않는다.** 반증 루프는 `turnOrder`를 돌며 `hands.get(id) ?? []`로 접근하므로 이탈자를 **조용히 건너뛴다.**
→ 이탈자가 들고 있던 **카드 2~4장이 영구히 반증 불가능**해지고, 그 카드를 포함한 제안이 `"❗ 아무도 반증하지 못함 — 정답 후보!"`로 방송된다. 정답이 아닌데 정답 후보다.
**연쇄**: 봇은 "아무도 반증 못 함 + 내 패에도 없음"이면 **즉시 확신 고발**한다 → 유령 카드 하나가 봇 여러 명을 연쇄 오답·탈락시키고, `turnOrder`가 1명이 되면 "최후 생존 승리"로 끝난다.
**즉 사람 1명이 판 도중 브라우저를 닫으면 2~3라운드 안에 봇들이 집단 자살하고 판이 사고사한다.**
게다가 UI가 이를 유도한다 — 탈락 배너의 **유일한 버튼이 [메인으로]**다. **판을 가장 확실하게 망가뜨리는 버튼이 탈락자에게 제공되는 유일한 버튼이다.**
- 조치: `removePlayer` 대신 **`handoverToBot`** — `isBot=true; awayBot=true; connected=false` + `initBotKnowledge`(기존 손패로 노트 재구성). **`hands`·`turnOrder`를 절대 건드리지 않는다.** 대기실에서만 완전 삭제. 재접속 시 좌석 반환.
- `awayBot`인 봇은 `revealed` 전역 공유 예외 처리(§1.1과 겹쳐 과하게 강해지는 것 방지).
- 4뷰: `displayName(p)` 헬퍼를 `shared`에 만들고 3개 렌더러의 이름 라벨을 치환(1줄 × 3) → `🤖`(순수 NPC) / `💤`(대리 중인 사람 자리).

## 8.2 🔴 턴 타이머가 코드에 존재하지 않는다 — AFK 1명이 판 전체를 무한 정지 (P0 · 2h)
`clock.setTimeout`은 봇 경로 3곳뿐이고 **사람 턴 타임아웃은 0개다.** `handleEndTurn`은 당사자만 호출 가능 → **AFK 1명 = 무기한 정지.** 이탈 시엔 `allowReconnection(60)` 동안 `currentTurn`이 이탈자에게 고정돼 **최대 60초 완전 정지**이고, `connected` 필드는 스키마에 있으나 **클라이언트 어디에서도 읽지 않는다**(grep 0건).
- 조치: `turnEndsAt`을 스키마에 노출 + `armTurnClock()`(사람 45초 / `connected=false` 8초). **§7.5.1의 "제안 후 고발 30초 자동 종료"와 같은 프리미티브를 공유**하도록 인자화(중복 구현 방지). **사람이 1명뿐이면 클럭을 끈다** — 솔로 심사 경험은 그대로.
- 이탈 시 `allowReconnection`을 120초로 늘리되 **20초 시점에 `handoverToBot` 선행** → 60초 무정지가 20초 유예 + 봇 대행으로 바뀐다.
- **다인 페이싱**: `npcDelay()`가 `avgHumanTurnMs/2`를 **사람 수와 무관하게** 쓴다. 사람 4+봇 2, 평균 20초면 1라운드 ≈ **107초**. 게다가 `avg`가 단일 EMA라 **가장 느린 한 명이 모두의 봇 딜레이를 끌어올린다.** → `/(2 × humans)` + `humans≥2`면 `BOT_ACT_GAP`/`SPEAK_HOLD`를 700/1200으로. 규약("사용자 평균의 절반")은 **1인당 해석**으로 유지되므로 위반이 아니다(문서에 해석 명시).
- 4뷰: `turnEndsAt`은 DOM HUD에서만 소비 → 뷰 독립. 진행 바 width만 rAF로 갱신.

## 8.3 🔴 재접속이 "들어와지긴 하는데 아무것도 못 하는 상태"로 복구된다 (P0 · 1h)
- **(a) 손패가 돌아오지 않는다.** `hand` 메시지는 `startGame()` **단 한 곳**에서만 전송된다. 재접속 분기는 `connected=true`와 로그만 처리한다. → 새로고침하면 서버는 손패를 갖고 있는데 클라 `myCards`는 빈 Set → 손패 HUD가 "(잔치 시작 후 표시)"로 남고, 증거노트가 **내 패를 정답 후보로 표시**하며, **자기 카드로 고발해 자멸할 수 있다.**
- **(b) 추리 기록 전체가 소실된다.** `#log`는 순수 DOM이다. 증거 노트는 `localStorage`로 살아남지만 **"누가 무엇으로 반증했는가"는 어디에도 저장되지 않는다.** 재접속해도 사실상 처음부터 다시 하는 셈.
- **(c) 60초를 넘기면 영원히 못 돌아온다.** `handleStart`가 `this.lock()`을 호출하고 **어디에서도 `unlock()`하지 않는다.** Colyseus의 `joinById`는 잠긴 방을 **거부**하므로 초대 링크 재입장 불가이고, **`onJoin`의 "이미 진행 중인 게임입니다 (관전)" 분기는 도달 불가능한 죽은 코드**다(관전 입장은 구현되어 있지 않다).
- 조치: `sendHand(id)` 헬퍼로 재접속 시 재전송(6줄) · `publicLog`(최근 200) + `privateLog`(sessionId 키) → 재접속·관전 입장 시 `replay` 전송 · **`lock()` → `setPrivate(true)`**(목록에서만 숨기고 코드 참가는 허용, 이미 비공개방에 쓰는 API) + 관전 좌석.
- ⚠️ 관전자는 `freeCellIn` 점유 집합·`handleMove` 충돌·소환 대상 탐색에서 **반드시 제외**(안 하면 유령 몸통이 문을 막는 봉쇄 버그). 각 1줄.
- ⚠️ `privateLog`는 반드시 `client.send`로만 — CLAUDE.md의 "비밀 정보는 대상에게만 개별 전송" 규약.

## 8.4 🟠 대기실이 여러 사람을 전제로 만들어져 있지 않다 (P1 · 2h)
- **대기실 단계의 모든 서버 로그가 보이지 않는다.** `addLog`는 `#log`에 쓰는데 `#log`는 **`#gameScreen` 안쪽**이고 대기실 화면은 `#lobby`다. → "입장·퇴장·캐릭터 중복·방장 전용" 피드백이 **전부 무음으로 사라진다.** 두 사람이 동시에 같은 캐릭터를 누르면 진 쪽은 **클릭했는데 아무 일도 안 일어난다**(데이터는 서버가 권위 있게 지킨다).
- **사람을 구분할 이름이 없다.** `Player.name`은 `label(suspect)`뿐 — **닉네임 필드가 스키마에 없다.** 4명이 하면 목록이 "🐭/🐮/🐯/🐰"뿐이라 누가 내 친구인지 알 수 없고, 게임 중 로그도 사람/NPC 구분이 안 된다.
- **공개방 메타가 낡는다** — 대기실에서 캐릭터를 바꿔도 `syncMeta()`가 호출되지 않는다.
- **시작 경합** — 방장이 시작하면 즉시 `lock()`이라, 친구가 `joinById` 왕복 중이면 "없는 방" 오류를 본다.
- 조치: 대기실 전용 로그 라인 + 캐릭터 셀 낙관적 `.pending` · **닉네임 8자**(서버 새니타이즈 + `displayName()` 재사용) · `syncMeta` 호출 2곳 추가 · 시작 3초 카운트다운 + 버튼 라벨 `"잔치 시작 (사람 3 + NPC 3)"`.
- ⚠️ 닉네임은 사용자 입력이다. `renderTurnStrip`·`openTurnCircle`·`showCharInfo`가 **`innerHTML`을 쓰므로** 서버 새니타이즈에 더해 클라 이스케이프 필수(XSS).

## 8.5 🟠 리매치가 "같은 판 한 번 더"일 뿐이다 (P1 · 2h)
- **아무나 혼자서 리매치를 강행한다** — 방장 검사·동의·카운트다운이 전부 없다. 4명이 결과 화면에서 정답을 보는 중에 한 명이 누르면 나머지는 보드로 끌려간다.
- **리매치는 NPC를 재충원하지 않는다**(충원 루프가 `handleStart`에만 있다) → 3명이 나간 뒤 리매치하면 **3인 판**이 되고 덱 구성·공통단서 규칙이 어긋난다.
- **선공이 영구 고정** — `ids[0]` = 입장 순서라 **방장이 모든 판에서 선공**이다. 이미 있는 주사위 연출 자산이 놀고 있다.
- **판 사이에 아무것도 누적되지 않는다** — 승수·시리즈 필드가 스키마에 없다. **한 판 더 할 이유가 게임 안에 없다.**
- 조치: 리매치 **과반 합의**(사람 1명이면 `need=1`이라 솔로 경험 동일) · 충원 루프를 `startGame`으로 이동 · **선공 셔플 + 기존 주사위 오버레이 재사용**(단 §7.10의 오버레이 큐에 `dice 80` 우선순위로 편입할 것) · `roundNo`+`wins` 스키마로 **시리즈 스코어보드**("제3판 · 통산 2:1").
- **탈락자·반증자 정보 결손**: 반증이 성립해도 **반증한 당사자에게는 어떤 메시지도 가지 않는다** — 자기가 어떤 카드를 누구에게 노출했는지 모른다. 정보 추적이 전부인 장르에서 사람끼리 할 때 치명적이다(봇끼리는 서버가 다 알아서 드러나지 않았다). → `send("shown", {to, card})` 12줄.

# 9. 런타임 건전성 (3차 검수)

## 9.1 🔴 첫 3초 — 번들 2,130 kB 단일 청크 (P0 · 2~3h)
빌드 실측: `index-*.js` **2,130.36 kB (gzip 512 kB)**, 단일 청크. 분해하면 phaser 1,479 / three 527 / colyseus 76 / 앱 44 kB.
`main.ts`가 3개 렌더러를 **정적 import**하므로, 랜딩이 인터랙티브해지기 전에 Phaser + Three를 전부 받고 파싱한다. **심사자가 뷰1만 보고 나가면 Three 527 kB는 100% 낭비**이고, 공개방 목록이 뜨기까지 2.1 MB 파싱을 기다린다.
- 조치: 동적 `import()`로 Phaser는 `enterGame()`, Three는 three 분기 최초 진입 시. **선행 조건**: `pixel-scene`이 `game-scene`에서 상수를 가져오는 **순환 의존을 shared 이관으로 먼저 끊어야** pixel 청크가 phaser를 통째로 끌고 오지 않는다(§3 이행 목록과 동일 작업). 랜딩 진입 시 `void import(...)`로 선로딩, 뷰 드롭다운 `pointerenter`로 prefetch.
- **효과: 크리티컬 JS 2,130 → 약 120 kB (−94%).**

## 9.2 🔴 보이지 않는 뷰가 계속 돈다 — 루프 2개·컨텍스트 2개·프레임당 강제 레이아웃 2회 (P0 · 1.5h)
Phaser `SceneManager.update()`는 **`visible`을 검사하지 않는다** — `setVisible(false)`는 **그리기만 멈추고 `update()`는 계속 돈다.** `PixelScene.update()`에는 자기 방어 가드가 있는데 **`GameScene.update()`에는 없다** → 뷰2·3에서 매 프레임 `getBoundingClientRect()`가 실행되고, 동시에 `IsoView.loop()`가 자기 RAF로 돌며 **또** 호출한다.
→ **뷰2·3에서 RAF 2개 / 라이브 WebGL 컨텍스트 2개 / 프레임당 강제 동기 레이아웃 2회.** 144Hz면 초당 288 콜백·288 리플로우.
- 조치: `setStage`에서 `three ? game.loop.sleep() : game.loop.wake()`. **`GameScene.update()`에 `isVisible()` 가드를 넣으면 안 된다** — 뷰4에서 GameScene은 invisible이지만 카메라를 돌려야 하고 PixelScene이 그걸 미러링한다. 정확한 축은 "three 뷰인가"다.
- 인셋을 프레임마다 읽지 말고 `ResizeObserver` + 드래그 핸들러에서만 갱신하는 캐시로. **§7.8은 가드의 정확성을 고치지만 프레임당 리플로우는 그대로 남는다** — 같은 함수를 손대는 김에 함께.
- `IsoView.setActive(false)`가 **말풍선 타이머를 정리하지 않는다** → 숨겨진 레이어에서 타자기가 계속 돌고 DOM이 남는다.
- 📌 **§7.8 정정**: null 가드가 아니라 **zero-rect** 문제다. `if (!el) return 0`은 이미 있고, `display:none`일 때 `getBoundingClientRect()`가 0을 반환해 `innerWidth - 0`이 되는 것이 원인이다(조치 문구는 그대로 유효).

## 9.3 🔴 `dispose()` 0건 — 뷰 왕복마다 GPU 자원이 쌓인다 (P0 · 2h)
`grep dispose apps/client/src` → **0건.** Three는 geometry/material/texture를 GC하지 않는다.
`setAssets()`는 `scene.remove` + `clear()`만 하고 다음 프레임의 `syncState()`가 전부 새로 만든다. **왕복 1회당 geometry 18+ / material 36+ / texture 28+ 유출**(룸 텍스처 교체도 이전 텍스처를 dispose 없이 덮는다). `THREE.Cache.enabled`는 기본 `false`라 뷰3 재진입마다 같은 SVG 10장을 **재디코드 + GPU 재업로드**한다.
**이 경로는 로드맵의 간판 기능(뷰 인터스티셜·연표)이 정확히 유도하는 동선이다.** 10회 왕복이면 geometry 180 / texture 280이 남는다.
- 조치: `disposeObject()` 재귀 해제 + 공유 지오메트리 상수화(초기 geometry 49→24) + `applyTexture`에 `map?.dispose()` 선행 + `THREE.Cache.enabled = true`.
- ⚠️ **`THREE.Sprite`는 모듈 전역 공유 지오메트리를 쓴다 — geometry를 dispose하면 화면의 모든 스프라이트가 함께 죽는다.** 순진한 구현이 정확히 여기서 깨진다.
- **회귀 게이트**: 뷰1→2→3→4→1 **10회 순회 후 `renderer.info.memory`가 초기값 ±5 이내**면 통과. 지금 돌리면 우상향 직선이 나온다.
- 뷰1 부수: **타자기가 55ms마다 `setText()`를 호출해 캔버스 재렌더 + 텍스처 재업로드**를 시킨다(30자 = 30회, 6인 동시 발화면 초당 ~109회). 전체 텍스트를 1회 그리고 `setCrop`으로 마스킹할 것. **뷰4에 타자기를 추가할 때 같은 결함을 복제하지 말 것.**

## 9.4 🟠 저사양·고주사율 (P1 · 2h)
- `antialias: true` + `dpr 2` → Retina에서 **7.7 Mpx를 MSAA로** 매 프레임, 같은 크기 Phaser 캔버스가 하나 더 살아 있다.
- 드로우콜 ≈ 120 / 텍스처 바인드 ≈ 50. 스프라이트가 전부 `depthTest:false`라 **깊이 거부 없이 투명 패스에서 개별 드로우콜**. 통합그래픽에서는 필레이트보다 이 CPU 오버헤드가 먼저 막힌다.
- **`loop()`가 RAF 타임스탬프를 인자로 받지도 않는다** → `lerp` 계수가 프레임 수 기준이라 144Hz에서 60Hz 대비 2.4× 빨리 수렴한다. **§3(view-contract-spec)이 요구한 `k = 1 - exp(-dt/τ)`는 dt를 만들 클럭이 없어 현 구조로는 구현 불가**다 → `loop(t)` 시그니처 변경이 **선행 조건**.
- `webglcontextlost` 핸들러 **0건** — 컨텍스트 2개 + 텍스처 누수 + 메모리 압박 = 검은 화면 영구화.
- 조치: dt 클럭 · `antialias:false` + dpr 1.5 + p95 기반 적응 해상도(히스테리시스) · 컨텍스트 로스 핸들러 · (P2) 정적 스프라이트 아틀라스·기둥 InstancedMesh.
- ⚠️ **적응 해상도를 뷰4에 적용하면 안 된다**(도트 그리드가 깨진다) — 스케일러는 three 뷰 전용임을 계약에 명시.

## 9.5 🟠 `STAGES.push`만으로 뷰5 추가는 성립하지 않는다 (P1 · 3h)
push만으로 자동 편입되는 것은 **드롭다운 목록뿐**이고, 런타임은 `main.ts` **8곳**(kind 유니온 · say 라우팅 3분기 · `scene:[...]` 정적 배열 · three/pixel 분기 · IsoView 싱글턴 · `scene.run("pixel")` 리터럴 · setVisible 개별 호출 · 키보드 게이팅)을 손봐야 한다. FX 계약이 들어오면 9번째가 붙는다.
뷰5가 3D라면 IsoView 재사용 시 **§9.3의 미해제 재생성이 3배**가 되거나, 별도 렌더러면 **컨텍스트 3개**가 되어 브라우저가 가장 오래된 것을 회수하는데 핸들러가 없어 **뷰1이 영구히 검게 남는다.**
- 조치: `ViewContract`에 **직교하는 생명주기 축** 추가 — `mount()`(동적 import) / `setActive()` / **`tick(dt)`(드라이버가 dt를 준다 — 뷰가 자기 RAF를 갖지 않는다)** / `dispose()` / `contextCost`. `STAGES`를 `{ load: () => Promise<ViewLifecycle> }`로 → `kind` 유니온과 분기 8곳이 소멸하고 §9.1의 동적 import가 그대로 들어간다.
- **프레임 드라이버 1개가 활성 뷰의 `tick(dt)`만 호출** → **§9.2(루프 2개)와 §9.4(dt 부재)가 같은 변경으로 함께 해결된다.**
- **성공 신호: 뷰5 추가 PR의 diff가 `STAGES` 항목 1개 + 새 파일 1개.**
- ⚠️ 뷰2·3은 **인스턴스를 2개로 쪼개지 말 것**(컨텍스트가 늘어난다) — `contextCost: 1`을 두 stage가 공유한다고 계약에 명시.
