0.1 무엇이 load-bearing인가

상류 정의(docs/planning/brainstorming/20260714-game-ideas.md)는 “AI 없으면 게임이 성립 안 되는 설계”를 요구한다. 이 프로젝트에서 그 조건을 지는 것은 에이전트 계층이다.

  • 07-18 회의에서 “심사자는 링크를 눌러 혼자 플레이한다”는 제약이 확정됐다. 클루는 3~6인 불완전정보 게임이라 상대가 없으면 규칙 자체가 작동하지 않는다.
  • addBot()이 빈 좌석을 십이지 캐릭터로 채우고, 각 봇은 자기만의 지식 상태(후보집합)로 소거 추리를 수행한다. 이 층을 빼면 1인 게임이 되어 제출물 ①(플레이 가능한 빌드) 요건 자체가 무너진다 → load-bearing.
  • 표현 계층(LLM)은 load-bearing이 아니다. 그렇게 설계했다. 이유는 §0.2.

초판 오류초판은 “load-bearing AI = 표현 전용”이라 썼다. 상류 용어를 뒤집어 쓴 것이며, 같은 문서의 “LLM 장애와 무관하게 게임은 정상”과 자기모순이었다. §0.3에서 정정한다.

0.2 왜 판정에서 LLM을 배제했는가 — 설계 판단 4근거

1. 환각이 곧 규칙 위반이 된다

반증은 “내 카드 중 제안 3장과 일치하는 것”이라는 전칭 판정이다. LLM이 이를 하면 없는 카드로 반증(위양성)하거나 가진 카드를 놓치는(위음성) 순간 정답이 도달 불가능해진다. 게임이 “틀리는” 게 아니라 끝나지 않는다.

2. 재현성이 없으면 검증도 없다

temperature 0.95 생성기는 같은 입력에 같은 출력을 주지 않는다. 판정이 여기 걸리면 버그 재현이 불가능하고 밸런스 시뮬레이션(1만 판)도 원리적으로 못 돌린다. 진실값을 규칙 함수로 고정했기에 판을 오프라인에서 1만 번 재생할 수 있다.

3. 치트 불가능성은 “안 준다”로만 증명된다

this.solution은 private이고 GameState 스키마에 없어 동기화 자체가 안 된다. 손패도 서버 전용 Map에 두고 해당 클라에게만 전송하며 LLM 프롬프트에도 넣지 않는다(예외 1건은 §2.2). “정답을 알려주고 말하지 말라고 지시”하는 방식은 인젝션 한 번에 무너지지만, 주지 않은 정보는 새어나갈 수 없다.

4. 무료티어에서 판정은 못 산다

판정을 LLM에 걸면 호출이 행동에 비례해 폭증하고 429 한 번에 게임이 멈춘다. 표현에만 걸면 429는 말투가 단조로워지는 것으로 끝난다.

LLM을 표현에 가둔 것은 능력 부족의 인정이 아니라, 검증 가능성과 가용성을 사기 위해 지불한 설계 비용이다. 그래서 본 문서의 본론은 “AI를 어떻게 게임에 넣었나”가 아니라 “AI를 어떻게 지휘·검수했나”(§2 · §3 · §7)다.

  2. 수신자가 이미 아는 정보다 — 같은 카드가 peek 메시지로 평문 전달된 뒤에 대사가 나간다.
  3. 출력이 봉인된다 — LLM 문장은 당사자에게만 가고 나머지 전원에게는 "(귓속말)"만 브로드캐스트된다. 흘려도 도달 대상은 이미 그 정보를 가진 1명뿐이다.
  4. 그 카드들은 정의상 전부 비정답이다(덱은 정답 3장을 제외하고 구성된다).

07-28 3차목표 길이를 내렸다 — 상한 40은 불변

라이브 실측에서 원문의 22%가 40자를 넘겨 폐기되고 있었다(§4 구현 결과). 상한을 올리는 대신 모델에게 주는 목표를 내렸다.

  • 32자 유도 — 관측된 최대 원문 50자 = 상한 40 대비 초과율 1.25배. 같은 초과율이 유지된다면 목표를 LINE_MAX / 1.25 = 32로 뒀을 때 최악의 원문이 40자 안에 들어온다 (LINE_TARGET_LOUD). 제안은 페이싱 예산(§6.2)이 더 빡빡해 25자(LINE_BUDGET_SUGGEST)를 그대로 쓴다.
  • 어절 앵커 — 모델은 글자를 못 세지만 어절은 센다. 목표를 «어절 N개 이하»(target / 4, 한국어 어절 ≈ 3자 + 공백)로 함께 주고, 시스템 지시에 실제 길이 예시 3개(“그 셈속이 훤히 보이는구먼 = 14자” 등)를 넣었다. 문구를 베끼지 말라고 못 박아 대사 다양성은 유지한다.
  • 규약을 느슨하게 한 것이 아니다 — LINE_MAX 40 · LINE_MIN 12 · LINE_BUDGET_SUGGEST 25는 전부 그대로다. 바뀐 것은 프롬프트가 요구하는 목표뿐이다.

07-28 3차캐시 적중률 0%는 고장이 아니라 설계가 예측하는 값이다

키가 진실값 조합이므로 키 공간은 용의자 12 × 장물 6 × 장소 9 × 페르소나 12 × disproved 2 = 15,552이고 한 판의 발화는 약 30건이다 → 기대 충돌 0.03건. 한 판에서 캐시가 맞을 일이 원리적으로 거의 없다.

  • 적중률을 올리려면 3요소를 키에서 빼야 하는데, 그러면 캐시된 문장이 다른 제안의 라벨을 말하게 된다 — 정확히 §3 C4가 blocking으로 막는 위반이다. 그래서 의도적으로 올리지 않았다. 캐시는 “적중률 지표”가 아니라 같은 진실값 조합이 반복될 때의 호출 절약 장치다.
  • GET /health에 cache{size, max, lookups, keyFields}를 노출한다 — hits: 0만으로는 “고장”과 “칠 일이 없었다”가 구분되지 않는다. lookups(조회 시도 = 적중률의 분모)와 keyFields(무엇이 키인가)를 함께 내보내야 0이 설명된다.
  • 같은 이유로 normalizeTiers(절단이 어느 단계에서 살렸는가 · sentence/clause/word/drop)를 추가했다. 폐기율 0%가 “안 잘렸다”인지 “잘 잘랐다”인지를 숫자가 말한다.

폴백의 설계 의도와 그 대가 정직 항목

추임새는 LLM이 죽어도 캐릭터색을 유지하기 위한 것이다. 그 결과 폴백과 LLM 출력이 육안으로 구분되지 않는다. 2026-07-27 라이브 실측에서 대사 5/5가 폴백이었음에도 “AI가 꺼져 있다”는 사실이 화면에 전혀 드러나지 않았다. 가용성을 위한 설계가 관측 가능성을 죽인 것이다. → §4가 해소를 요구사항으로 규정한다.

2.6 4뷰 공통 전달 계약 — 표현 계층은 렌더러에 독립이다

서버는 렌더러를 모른다. broadcast("say", { id, from, text }) 하나만 내보내고 4개 뷰가 전부 동일한 showBubble(id, text) 시그니처를 구현한다 (뷰1 game-scene.ts / 뷰2·3 iso-view.ts 공용 / 뷰4 pixel-scene.ts). 라우팅은 main.ts 한 곳뿐.

  • P6 절단 구제 불변식 07-28 3차 신설 — 3단 절단(§2.3)이 규약을 지킨 채로 문장을 살리는지 매 실행 검사한다. 합성 코퍼스 16종(41~50자, 종결부호를 끝에만 둔 형태)에 대해 ① 상한 이내 ② 하한 이상 ③ 어절 중간 절단 0 ④ C3 통과 ⑤ ops에 truncate 기록 — 5개를 전부 만족해야 PASS. 공백 없는 덩어리 2종은 폐기돼야 PASS다. 결과: 이전 규칙 생존 0/16 → 현재 16/16.

  • 자리는 띄우되 값은 말하지 않는다. 0 · 0 · 0은 여전히 그리지 않고, 값 자리는 확정 문안의 — 관례로만 채운다. “아직 측정이 없다”와 “0건이었다”는 다른 주장이고 화면이 후자를 말하면 안 된다.
  • 서버 빈 스냅샷의 avgMs: 0이 평균 0.0s로 새던 경로도 같이 막았다.
  • ✨/♻/⚙ 범례를 넣었다 — 기호만 있고 뜻이 없으면 계측이 아니라 장식이다.

실측 1판(23제안 · 24발화 · 07-28 2차 시점): llm 19(avg 923ms) · cache 0 · fallback 4(전부 toolong). 그 뒤 07-28 3차에 fallback 9/41(22%)이 재현돼 목표 길이 인하 + 3단 절단으로 대응했고, 실호출 16콜 검증에서 폐기 0% · 준수율 1.00이 나왔다(§2.3). ⚠ 표본 8건이라 확정이 아니다 — 한 판 완주 후 /health 재확인이 남아 있다. 키 없이 같은 판을 돌리면 첫 발화부터 fallback(nokey) — §4.1 장애가 즉시 드러난다.

4.1 실제 장애 사례 — 이 절이 요구사항인 이유 (2026-07-28 해결)

라이브에서 NPC 대사가 100% 규칙 폴백으로 나가고 있었고, 화면에도 로그에도 아무 신호가 없었다.

  • 원인 — thinkingConfig.thinkingBudget: 0이 400 INVALID_ARGUMENT로 거부됐다. gemini-flash-lite-latest 별칭이 해당 파라미터를 받지 않는 세대로 이동했기 때문이다. 그 400을 if (!res.ok) return null이 흡수해 전 호출이 폴백으로 빠졌다.
  • 키·쿼터는 정상이었다 — 모델 목록 조회 200, thinkingConfig만 빼면 200과 정상 대사(5/5). 즉 운영 문제가 아니라 요청 파라미터 문제였다.
  • 왜 늦게 발견됐나 — 실패 로그가 [narrate] HTTP 400으로 상태코드만 남겨 사유가 없었고, 폴백이 §2.5의 설계대로 캐릭터색을 유지하므로 육안으로 구분되지 않았다.
  • 조치 — thinkingConfig 제거 + 실패 로그에 응답 본문 포함. 배포 후 라이브 재검증 12/12 LLM · 폴백 0건.

이 사건이 §4의 5개 요구사항을 정당화한다. 가용성을 위한 폴백은 관측 가능성을 갖추지 않으면 장애를 숨기는 장치가 된다. source/ms 계측과 AI 카운터 칩이 있었다면 첫 판에서 드러났을 문제다.

6. 사람다운 템포 (엔진 규약)

  • NPC 딜레이 = 사용자 평균 턴 시간의 절반. clamp(avg/2, 800, 1600), 데이터 없으면 3000
  • EMA avg = avg×0.6 + dur×0.4, 사람 턴만 표본에 넣는다 (봇 턴을 섞으면 봇이 자기 속도를 자기가 정하는 되먹임이 생긴다)
  • 턴 내 2박자: 이동 → BOT_ACT_GAP 600 → 제안 → 대사 길이에 비례한 홀드. 타이핑 중 턴을 넘기면 카메라가 튄다
  • 해소다인 avg가 모든 사람의 단일 EMA라 가장 느린 한 명이 모두의 봇 딜레이를 끌어올리던 문제 → avg/(2×humans)

6.1 07-28 정정 — 고정 SPEAK_HOLD는 폐기됐다

초판은 SPEAK_HOLD 2400 고정이었다. 그런데 클라 말풍선 수명은 bubbleLifeMs(text) = max(1800, 글자수×55 + 2600)이라 모든 대사에서 서버가 먼저 턴을 넘겼다 — 40자면 4800 대 2400으로 2배 어긋난다. 위의 “타이핑 중 턴을 넘기면 카메라가 튄다”를 문서가 적어두고 코드가 100% 위반하고 있었던 셈이다.

조치 — 상수를 삭제하고 speak()가 실제 방송한 문장을 반환하게 바꿔 bubbleLifeMs(line)으로 타이머를 건다. 이 함수를 packages/shared에 DOM 의존 없이 두어 서버·클라가 같은 함수를 쓴다(정합을 문서가 아니라 코드로 보증).

6.2 07-28 후속 — 남은 레버는 대사 길이였다 해소

문서가 “12~40자”를 규약으로 명시해놓고 폴백 제안 대사가 평균 47자였다. 규약을 어긴 것은 프롬프트가 아니라 우리가 쓴 템플릿이었다.

  • 홀드 타이머를 거는 것은 제안 대사뿐이다(고발·계략은 즉시 다음 동작으로 간다). 그래서 제안만 25자 예산으로 조이고 고발·계략은 40자까지 열어 클라이맥스 대사의 캐릭터색을 지켰다 — 제안 47.1 → 21.3자.
  • BUBBLE_HOLD_MS 2600 → 1200. 2600은 뷰별 인라인 리터럴을 옮겨 적은 값이라 유도 근거가 없었다. 읽기 속도 12자/초에서 타자기가 이미 소비하는 몫을 빼면 (83−55)×40 = 1120 → 1200. TYPE_MS 55는 AI 활용의 유일한 가시적 증거라 불변.
  • 결과: 봇 1턴 7.6초 → 3.8초(실측 80표본 평균 3,784ms · 계산식과 11ms 오차).

⚠ 남은 간극 — 그리고 계측이 이 절의 서술 2건을 반증했다

LLM이 켜져 있으면 Gemini 왕복이 홀드 앞에 붙는다. 대사 길이가 아니라 narrate()를 await한 뒤 방송하는 구조 비용이다. 이 문장은 원래 “왕복 ~1.2초이며 캐시 히트 시엔 사라진다”고 적었는데, §4 계측을 붙여 재보니 둘 다 틀렸다:

  • 왕복 실측 평균 926ms(756~1194ms) — 1.2초보다 낮다.
  • 캐시 히트 0건 / 24발화. cacheKey가 제안 3요소 + disproved 조합이라 한 판에서 같은 조합이 거의 재현되지 않는다. 완충 논리가 실제로는 발동하지 않으므로 왕복은 상시 비용이다.
    07-28 3차 후속이것은 고장이 아니라 키 공간 15,552 대 판당 발화 30이 예측하는 값이며, 올리려면 C4를 깨야 하므로 의도적으로 올리지 않기로 확정했다(§2.5).
  • LLM 응답의 17%(4/24)가 40자를 넘겨 폐기됐고, 살아남은 문장도 31~39자로 제안 예산 25자를 크게 넘었다. 페이싱의 실질 레버는 왕복보다 출력 길이 강제일 수 있다.
    07-28 3차그 레버를 당겼다 — 목표 길이 인하 + 3단 절단으로 폐기 22% → 0%, 최대 원문 50 → 34자(§2.3). 상한을 40 → 50으로 올리는 반대 방향은 봇 1턴 +550ms · 판당 +15.4초라 기각했다.

해법 후보를 07-28에 의도적으로 착수하지 않았다. 홀드 기점을 LLM 도착 시각으로 옮기면 총 턴시간은 그대로이고, 폴백 방송 시각에 고정하면 LLM 문장의 화면 노출 시간이 그만큼 깎인다 — LLM 문장이 곧 AI의 가시적 증거인데 그것을 줄이는 거래다. 선생성은 disproved가 doSuggestion 이후에야 정해져 규칙 엔진 결정을 앞당기거나 이벤트당 2콜이 필요하다. 요구사항 · 결정 필요

8. 본행사 계승 — 자유 심문 · 거짓말/뇌물 축

07-18 회의에서 확정한 차별점 중 자유 심문(자연어 질의) · 정직 | 뇌물(거짓말) 축은 사전과제 빌드에 구현되지 않았다. 숨기지 않고, 왜 미루었고 어떻게 얹을지를 명시한다.

8.1 왜 사전과제에서 하지 않았나

1. 경계가 이동한다

자유 심문은 진실값 경계를 LLM 쪽으로 옮긴다. 자연어 질의를 규칙에 비추어 판정하려면 판정 결과가 LLM 출력에 의존하게 된다. 경계를 먼저 세우고 검증 프로토콜을 갖춘 뒤에 넘어가야 할 순서지, 반대가 아니다.

2. 검증 없는 기능 추가는 감점

D-14에 새 축을 넣으면 §3의 검사 5종을 전부 새로 설계해야 하고 실행할 시간이 없다. 검증할 수 없는 기능은 넣지 않는다가 이 프로젝트의 규칙이다.

3. 무료티어 모델이 깨진다

현재는 “이벤트당 1콜 + 캐시”라 상한이 있다. 자유 심문은 사용자 입력당 1콜이며 자연어라 캐시도 듣지 않는다.

8.2 본행사에서 어떻게 얹는가 — 3단 파이프라인

경계를 옮기는 게 아니라, LLM을 경계의 양쪽 끝에 두 번 쓴다.

입력 예 — 사용자 자연어 너 어제 후원에 있었지?

① 질의 정규화 LLM · 표현 → 구조

출력은 자연어가 아니라 고정 스키마 슬롯: { target, category: suspect|weapon|room, value: <27 라벨 중 하나> | null }

  • 스키마 · 사전 밖 값은 즉시 폐기 → 무슨 말인지 모르겠소 폴백
  • LLM이 여기서 낼 수 있는 최악은 “질문을 잘못 알아듣는 것”이지 게임 상태 변경이 아니다
▼

② 판정 규칙엔진 · LLM 없음

슬롯을 hands / solution에 대조 → truth. 정직/거짓 상태와 뇌물 자원도 규칙엔진이 결정.

거짓을 말하기로 정해지면 거짓 답변의 내용까지 규칙엔진이 후보에서 고른다. LLM이 거짓 내용을 창작하면 그 거짓은 환각과 구분할 수 없고 §3의 C4·C5가 원리적으로 작동하지 않는다.

▼
