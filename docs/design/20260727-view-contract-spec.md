# 4뷰 표기 계약 명세 (view-contract / view-consts / ZODIAC_COLOR)

> 작성 2026-07-27 · **개정 2026-07-28(구현 반영)** · 사람용 `.html` 동봉 · 상위 문서: `20260727-improvement-roadmap.md` §2·§7.8~7.11
> 목적: **뷰5를 추가해도 표기가 갈라지지 않게** 정보를 타입으로 강제한다. 표현은 뷰의 자유로 남긴다.

## 0. 왜 지금인가
`TYPE_MS`·`BUBBLE_HOLD_MS`·`CAM_SWITCH_DELAY`·`MOVE_COOLDOWN_MS`·`PLAYER_COLORS`가 **3개 렌더러 파일에 각각 리터럴로 중복**돼 있다. 값이 갈라진 게 아니라 **갈라질 수밖에 없는 구조**다(실제로 뷰4는 말풍선 상수를 안 쓰고 `3200`을 인라인한다). 상수를 `packages/shared`로 올리면 서버도 같은 값을 보므로 NPC `SPEAK_HOLD`와 말풍선 수명의 정합까지 타입으로 잠글 수 있다.

**설계 원칙 — "정보는 강제, 표현은 자유"**
1. 모든 메서드는 **서버 진실값에서 파생된 순수 데이터**만 받는다. Phaser/Three/DOM 타입이 계약 파일에 하나도 등장하지 않는다(그래서 `shared`에 둘 수 있다).
2. 모든 메서드의 반환형은 `void`. **반환형을 두는 순간 호출부가 표현을 알게 되고 4뷰는 "스킨 4개"가 된다** — 진화 서사의 정면 위배.
3. 강제하는 것은 "이 사실을 반드시 화면에 남겨라"뿐. 어떤 오브젝트로 남길지는 뷰의 몫.
4. 뷰5 추가 시 `implements ViewContract` 한 줄이 미구현을 컴파일 타임에 잡는다.

### 1.5 비밀 통로 표기 (2026-07-28 추가 · 로드맵 §2.5)
통로 선은 **정보이면서 동시에 방해물**이다. 보드를 가로지르는 대각선이라 항상 선명하면 방·토큰보다 먼저 눈에 들어온다(사용자 피드백). 지우면 정보가 사라지므로, **평소엔 잠그고 커서가 오면 연다.**

| 상수 | full | reduced | 의미 |
|---|---|---|---|
| `PASSAGE_ALPHA_IDLE` | **0.09** | 0.09 | 기본 밝기 — "있다"만 알리는 하한 |
| `PASSAGE_ALPHA_HOVER` | **0.75** | 0.75 | 커서가 근처일 때 |
| `PASSAGE_HOVER_PX` | **34** | 34 | 커서–선 **화면 거리** 임계 |
| `PASSAGE_FADE_MS` | **160** | 0 | 전환 시간(감속 프로파일에서만 0) |

- **임계는 화면 거리다 — 뷰마다 재는 방법이 다르다.** 뷰1·4는 `PASSAGE_HOVER_PX / zoom`으로 **줌을 나눈다**(안 나누면 축소 시 화면상 먼 선이 켜진다). 뷰2·3은 42° 피치라 월드 거리가 화면 거리와 무관하므로 **선의 양 끝점을 화면에 투영해** 잰다.
- 계약상 강제되는 정보는 `setPassages(links)`의 "통로 쌍이 존재한다"뿐이고, **밝기 정책은 4뷰가 같은 상수를 공유하는 표현**이다 — §0 원칙 3("정보는 강제, 표현은 자유")과 충돌하지 않는다. 단 **상수는 공유해야** 뷰마다 "언제 보이는가"가 갈리지 않는다.

## 4. `ZODIAC_COLOR` 12색 팔레트

**설계**: 현재 배정이 `ids.indexOf(id) % 6`(**접속 순서**)이라 같은 캐릭터가 판마다·판 도중에도 색이 바뀐다. 키를 `suspect`(로비에서 확정, 판 중 불변)로 바꾸면 결정론이 공짜로 나온다.
계열은 오방정색 **적(赤)·청(靑)** + 오간색 **벽(碧)·자(紫)** 4계. 보드가 이미 갈색·금색 난색이므로 토큰을 한색+적 쪽에 두면 도형/배경 분리가 생기고, **황(黃) 계열을 뺀 것이 금색 현재-턴 링과의 충돌을 원천 제거**한다.
배치는 라틴방진: `family = i % 4`, `tier = (i + ⌊i/4⌋) % 3` → 각 계열이 3명도단을 정확히 한 번씩, 인접 index끼리 계열·명도단이 동시에 달라진다.

### 4.1 검증 (CIEDE2000 · Viénot–Brettel–Mollon 색각 시뮬레이션)
**66쌍 전수 최소 ΔE00 — 정상 10.0 / 2형 9.6 / 1형 9.6 / 3형 6.9.**
- **2형·1형에서 충돌(ΔE00 < 6)하는 쌍은 0건.** 최악값 9.6은 "인접 배치 시 확실히 다른 색"으로 읽히는 구간(카테고리 구분 권장선 ≈ 5).
- 성립 이유: 계열을 **색상만이 아니라 채도까지** 다르게 잡았다. 2형에서 청·자는 둘 다 청색으로 수렴하지만 청(C39)→`#6969b7`, 자(C25)→`#8e8ea7`로 **채도가 갈리고**, 벽(C25)은 거의 무채(`#9f9fa5`)로 떨어져 **세 번째 극**을 만든다. 즉 2형의 잔존 공간은 (명도 × 청–황) 2차원이고 그 위에 12점을 배치했다.
- 대조군: **현행 6색은 2형에서 라임·그린·레드가 수렴**해 최대 3명이 구분 불가다. 12색이 6색보다 CVD 성능이 좋은 것은 색 수가 아니라 **축 설계의 차이**다.
- ⚠️ **회색조 단독으로는 12색이 분리되지 않는다**(최소 인접 ΔL* 0.2). 이는 튜닝 실패가 아니라 **1차원 축에 12점을 넣는 문제의 수학적 한계**다. 흑백 인쇄 계획이 없고 2형/1형은 청–황축이 살아있으므로, 검증 기준을 회색조가 아닌 실제 색각이상 2차원으로 잡았다.
- 배경 대비: 밝은 방바닥·잔디에서 1.0~1.3까지 떨어지는 색이 있다(`sheep` vs 방바닥 1.02). **설계상 허용** — 배경 분리는 아웃라인이 담당한다. 계약에 **모든 토큰 색면은 최소 2px 아웃라인**을 명문화하고, 뷰2·3의 `disc`에는 현재 없으므로 `RingGeometry(0.42,0.46)` 흰 테두리를 추가한다.

### 4.3 `?cvd=1` 대체 표기
색을 **끄지 않고 보강**한다(색을 쓸 수 있는 사용자의 정보량을 깎지 않기 위해). 인코딩은 팔레트 구조를 그대로 노출 — **계열(4) × 명도단(3)**, 최대 3개만 세면 된다.
```
8×8 도트 셀
  계열 바: 적 ▌좌변 · 벽 ▀상변 · 자 ▐우변 · 청 ▄하변  (2px)
  명도 핍: T0 ● / T1 ●● / T2 ●●●                      (중앙 가로 1열)
  색: 바·핍 모두 흰색 고정 — 색 대체 표기가 색에 의존하면 의미가 없다
```
`localStorage.zc_cvd`에도 저장해 재접속에 유지(URL 파라미터를 매번 붙이게 하지 않는다).
