# plan: 죽어 있던 스크롤바 도색을 되살린다 — 전역 한 줄이 저장소 전체의 스크롤 신호를 끄고 있었다

status: done(2026-08-28) · created: 2026-08-28 · src: 개선 루프 21회차 (플랜 40 큐 1번)

## goal
20회차가 우측 컬럼에서 찾은 원인을 **저장소 전체에** 적용한다.
`index.html`의 전역 한 줄이 `.rp-body`·`.room-list`·`.modal`·`.rp-col`·`.cx-rail`·문서의
스크롤바를 **정지 화면에서 전부 안 보이게** 만들고 있었다.

## 진단 — 한 줄이 두 가지를 동시에 했다
```css
* { scrollbar-width: thin; scrollbar-color: var(--wds-line-normal) var(--wds-bg-normal); }
::-webkit-scrollbar { width: 9px; … }   /* ← 이 3줄이 죽어 있었다 */
```
Chromium은 표준 속성이 **non-auto면 `::-webkit-scrollbar`를 통째로 무시**하고,
그때 macOS에서는 **오버레이(자동 숨김)** 스크롤바가 된다. 그래서

1. 바로 아래 9px 도색 3줄(주석: 「스크롤바 톤 통일」)이 **죽은 코드**였다 — 의도한 톤이
   화면에 나온 적이 없다.
2. 전 스크롤 영역이 **정지 화면에서 단서 0**이었다.

9회차는 그 결과(「`::-webkit-scrollbar` 폭이 레이아웃상 0」)를 **플랫폼 한계로 읽고**
스크롤바를 기각한 뒤 그라디언트 오버레이를 깔았다 — 그 오버레이가 20회차에 **AA 위반**으로
걷혔다. **두 회차의 우회가 전부 이 한 줄에서 나왔다.**

## 처방
```css
::-webkit-scrollbar { … }                      /* Chromium·Safari — 9px 도색이 산다 */
@supports (-moz-orient: inline) {              /* Gecko만 */
  * { scrollbar-width: thin; scrollbar-color: …; }
}
```
- 20회차의 국소 `.rp-body, #aiDetail { scrollbar-*: auto }`는 **중복이라 제거**.
- **`.cx-rail`(도감 가로 캐러셀)** 은 자체 `scrollbar-width: thin`으로 **같은 자해**를 하고
  있었다. 지우고 **어두운 면 전용 도색**을 줬다 — 전역 도색은 트랙이 `--wds-bg-normal`(밝음)이라
  이 레일 위에서 뒤집힌다(§1.5 «어두운 면 2종»과 같은 사정).
  엄지 `--wds-accent` ↔ 레일 배경 **9.47~10.41:1**(1.4.11 하한 3.0).
  15칸 캐러셀에서 «옆에 더 있다»는 신호가 **처음으로 화면에 나왔다** — 단
  **창 폭 ~1200px 미만에서만**이다(1280px에서는 레일이 안 넘친다).

## 실측
| 지정 | 폭 | 정지 화면 도색 |
|---|---|---|
| `thin` + 색 (기존 전역) | 0px | 없음 |
| `auto` + 색 | 0px | 없음 |
| **도색 규칙만**(`@supports`로 표준 속성 제외) | **9px** | **그려짐** |

- 도감 레일: 1280px에서는 안 넘침(`scrollW 1160 = clientW`) · 760px에서 **11px 스크롤바**,
  캡처에서 금색 엄지 확인.
- 게이트 PASS 68 · FAIL 1(`roomlist-ended` 플레이크) · `typecheck` · `verify:quick` 통과.
- 랜딩·대기실은 카드가 뷰포트에 들어가 **문서 스크롤바가 안 생긴다**(18회차 축 무영향).

## 🔴 검수가 뒤집은 것 ① — 판별식이 **어디에서도 실행되지 않았다**
초안은 `@supports not selector(::-webkit-scrollbar)`였다. **Firefox 153**(2026-07-21 ·
차기 ESR)이 이 의사요소를 **셀렉터로만 인식**해 `selector()`가 **true**를 주면서
**도색은 구현하지 않는다.** 그러면
- Chromium: `true` → 블록 skip → 도색 사용 ✅ (의도대로)
- **Firefox: `true` → 블록 skip → 표준 속성도 안 걸림 + 도색도 없음 → 스타일 0** ❌

즉 **자기가 유일하게 겨냥한 브라우저에서 순수 회귀**였다(변경 전에는 `thin` + 색이 걸렸다).
→ **Gecko 전용 속성**으로 바꿨다. `-moz-orient`가 Chromium에서 `false`임은 실측 확인.
`[미확인]` **이 저장소에 Firefox 실측 수단이 없다** — Gecko 쪽은 사람이 한 번 봐야 한다.
`.cx-rail`의 `scrollbar-width: thin` 제거도 같은 이유로 위험했다(Firefox의 **유일한** 신호였다).
전역 `*`가 Gecko에서 살아나면 그 레일도 함께 덮인다.

## 🔴 검수가 뒤집은 것 ② — 도감 레일 대비를 **엉뚱한 색과** 쟀다
- 초안 「엄지 ↔ **레일 배경** 9.47~10.41」 — 1.4.11이 보는 인접색은 **트랙**이다.
  실제 값 **7.11~8.14:1**(통과는 하지만 근거가 틀렸다).
- `border: 2px`는 **엄지 위에 합성된다**(`background-clip` 기본값 `border-box`) →
  9px 바에서 **눈에 보이는 엄지는 5px**이다. 전역 엄지도 같은 구조다.
- 🔴 **전역 `::-webkit-scrollbar-thumb:hover`가 레일 엄지를 덮는다.** 특이도가
  `.cx-rail::-webkit-scrollbar-thumb`(0,1,1)와 **동률**이고 전역이 뒤에 있어 이긴다 →
  hover에서 `--wds-label-assistive`가 트랙 대비 **2.83 / 2.47:1**로 **하한 미달**.
  같은 파일이 `.cx-thumb:hover` 특이도를 정확히 계산해 뒀는데 바로 옆에서 안 했다.
  → `.cx-rail::-webkit-scrollbar-thumb:hover`를 **밝히는 방향**으로 덮었다(11.22 / 9.80).

## 🔴 검수가 뒤집은 것 ③ — `.room-list` 여백은 «같은 규약»이 아니었다
`.rp-body`는 **있던 12px을 4px로 줄인** 것(순손실 1px)이고, `.room-list`는 원래 0인데
**더한** 것이다(4 + 스크롤바 9 = **13px 손실**). 안 넘칠 때도 4px을 잃어 바로 위
`.field input`(카드 폭 100%)과 **오른쪽 축이 어긋난다.** → **되돌렸다.**

## 🔴 검수가 찾은 것 ④ — 도색이 살아나면서 **드래그 스크롤 핸들러에 경로가 생겼다**
`enableDragScroll`은 `pointerdown`을 요소 전체에서 받는데, 스크롤바는 테두리 상자 안이지만
`clientWidth` **밖**이다. 오버레이(폭 0) 시절엔 **도달 불가였던 경로**다.
네이티브 엄지를 잡아 끌면 스크롤 위치는 정상이지만 이 핸들러가 `moved`를 세워
**뒤따르는 클릭 1회를 삼킨다**(증거 노트 칩을 한 번 못 누른다).
→ `e.offsetX >= el.clientWidth || e.offsetY >= el.clientHeight` 가드.

## 🔴 검수가 찾은 것 ⑤ — 반투명 패널 위 **불투명 트랙**
`.rp-panel` 본문 배경은 `rgba(255,248,239,0.9)`가 합성돼 `#E9E2DA`쯤인데 트랙 토큰
`--wds-bg-normal`(#FBF3E7)은 불투명이라 **패널 안에 더 밝은 9px 띠**가 섰다.
이 파일이 `--wds-line-normal`·`.sg-mine`에서 두 번 지적한 함정이다.
→ `.rp-body`·`#aiDetail` 트랙을 `transparent`로. 엄지 ↔ 합성 배경 **최악 3.47:1**.

## 🔴 정직하게 남기는 한계 — 실기 폰은 **엔진마다 다르다**(초안이 단정했다가 뒤집혔다)
초안은 「실기 iOS·Android는 오버레이라 폭이 0」이라고 **단정**했다. 근거가 없었다.
- **Android Chrome**: Blink 문서상 «`::-webkit-scrollbar`에 `width/height`를 주면 오버레이가
  클래식이 된다»(플랫폼 조건 없음) → **닿을 가능성이 높다.**
- **iOS Safari**: 그 의사요소를 안 그리고 오버레이만 쓴다 → **신호 0일 가능성이 높다.**
- 둘 다 **문헌 근거이고 실기 측정이 아니다.**

게이트로는 못 가른다 — 헤드리스 모바일 에뮬레이션은 클래식 스크롤바를 그리고 **9px을
레이아웃에서 가져간다**(실측: `mobile: true`에서도 `offsetW − clientW = 9`).
→ §사람 확인 항목을 그 사실대로 고쳐 넣었다. 폭 방향은 안전하다.
