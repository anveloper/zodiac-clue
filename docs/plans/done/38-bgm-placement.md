## 진단
`apps/client/index.html`
- `.bgm-ctrl` 기본값: `position: fixed; top: 12px; right: 12px; z-index: 40` (:76)
- 폰(`max-width:680px | max-height:500px`)·`pointer:coarse` 두 블록이 이걸
  **`top: 150px; right: 8px; z-index: 4`로 무조건 덮었다.**

`150px`의 근거는 «상단 우측 닫기 토글(`#rpToggle`)을 피한다»인데
**`#rpToggle`은 `#gameScreen` 안에 있다** — 랜딩·대기실엔 **존재하지 않는다.**
즉 카드 화면에서 150px는 **근거 없이 상속된 값**이다.

그런데 카드 화면은 `.center { min-height:100dvh; display:flex; align-items:center }`(:281) —
**세로 중앙 정렬 + 내용 의존 높이**다. 카드가 자라면 상단이 **위로 움직이고**,
오른쪽 정렬 컨트롤이 고정 150px 띠를 **가로지른다.** 두 번의 사고가 같은 자리인 이유다.

## 처방 — 카드 화면에선 기본값(`top:12px`)으로 되돌린다
```css
.bgm-ctrl { position: absolute; bottom: auto; right: calc(8px + var(--sa-r,0px)); left: auto; z-index: 4; }
body.no-scroll .bgm-ctrl { position: fixed; top: calc(150px + var(--sa-t,0px)); }
```
`150px`은 그 값을 필요하게 만든 화면에서만 산다. 두 media 블록에 같은 규칙을 넣는다
(적용 조건이 서로 다르고 어느 쪽도 다른 쪽을 포함하지 않는다).

**조건 표현은 새로 만들지 않았다.** 초안은 `body:has(#gameScreen:not(.hidden))`이었는데,
이 파일엔 이미 «게임 화면»을 뜻하는 관용구 `body.no-scroll`이 있고 `#scene-bg`(:97) ·
`#lobby-char`(:109) · `#leaf-bg`(:191) 세 규칙이 그걸 쓴다. `show()`가 `gameScreen`일 때만
붙이는 클래스라 조건도 정확히 같다(`main.ts:154` — 유일한 부착 지점). 같은 상태를
**두 가지 방법으로** 쓰면 다음 사람이 어느 쪽이 진짜인지 물어야 한다.

### 🔴 검수가 뒤집은 것 — `top`만 되돌리는 건 **부족했다**
초안의 논거는 «카드 화면에선 상한이 내용과 무관하다»였다:
`.center` padding이 카드 상단을 y≥16px로 고정하고 `#copyBtn`은 제목·부제 아래라 y≥90px —
BGM 띠(12~62)와 겹칠 수 없다. **이 논거는 `scrollTop = 0`에서만 참이다.**

카드 화면은 게임 화면과 달리 **`body.no-scroll`이 없어 문서가 스크롤한다**(`index.html:212`).
`.bgm-ctrl`이 `fixed`면 카드가 **그 밑으로 흘러 들어간다.**
직접 재확인(CDP · 390×844 · `.card{padding-bottom:900px}` 주입):

| 요소 | 스크롤 | `elementFromPoint` |
|---|---|---|
| `#joinBtn` | 373 | **`bgmVol`** |
| `#refreshRooms` | 433 | **`bgmVol`** |

즉 13·17회차의 고장이 «게이트가 보는 자리»에서 «게이트가 안 보는 자리»로 옮겨졌을 뿐이었다.
**S1은 스크롤 프로브보다 먼저 재고, 랜딩·대기실은 `vscroll: "allow"`다.**

### 처방 보강 — 카드 화면은 `position: absolute`
문서와 **같이** 움직이므로 문서 좌표에서 BGM(y12..62)과 카드 컨트롤(y≥110)이
**어떤 스크롤 위치에서도** 갈린다. 대가는 «긴 카드에서 같이 스크롤돼 나간다»이고,
그 편이 «보이는데 안 눌린다»보다 낫다.
같은 실측 재실행 → **BLOCKED: none** (7개 컨트롤 전부 자기 자신이 히트).

## 🔴 검수가 찾은 **별건** — 이번 회차에 안 고친 것 (근거를 주석에만 남겼다)
1. **`z-index: 4`가 «패널 아래»를 뜻한다는 주석은 거짓이었다.**
   `#gameScreen { position: fixed }`(:452)는 **스택 컨텍스트를 만든다** — 그 안의
   z:5·6·8·12·35·40은 서로만 겨루고, `<body>` 직계인 `#bgmCtrl`(z:4)은 **게임 화면 전체 위**다.
   실측 히트테스트로 확인: 우측 패널 위에서 `elementFromPoint` → `bgmToggle`.
   **파급 — `#endOverlay`(결과)·`#goalCard`(온보딩) 오버레이를 BGM이 뚫는다.** 데스크톱(z:40)도 같다.
   여기서 4든 40이든 결과가 같으므로 **값은 두고 근거만 지웠다.** 고치려면 BGM을
   `#gameScreen` 안으로 옮기거나 오버레이가 열릴 때 감춰야 한다 → 다음 회차 후보.
2. **`.bgm-vol`은 `width: 0`인데 실제 계산값이 22px이다**(`opacity: 0`).
   그래서 접힌 상태에서도 컨트롤 상자가 **82px**이고 보이는 아이콘(x335..379)보다
   **35px 왼쪽까지 히트한다** — 위 표의 차단자가 바로 이것이다.
   **S3(터치 하한)가 원리적으로 못 보는 «보이지 않는데 눌리는 영역»**이다.
   `pointer-events: none`만으로는 부족하다(컨테이너 `div`가 대신 먹는다) → 다음 회차 후보.
3. **coarse 태블릿(681px~)의 `150px`은 근거가 확인되지 않았다** — 그 구간엔 `#rpToggle`이
   없고(`display:flex`는 `max-width:680px` 블록 :1379에서만) 배너도 전폭이 아니다.
   **게이트 뷰포트가 폰·데스크톱 둘뿐이라 잴 수단이 없어** 값을 그대로 뒀다.
4. **150px의 지배적 사유를 주석에서 지웠다가 되살렸다** — 초안이 `#rpToggle`만 적었는데,
   그건 «패널이 열렸을 때만» 있는 부차 사유고 **상시 전폭인 턴 배너**(`.hud-turn` y10~74)가
   지배적이다. 이 주석을 믿고 다음 회차가 150을 줄이면 배너 밑으로 들어간다.
5. `:has()` 초안은 **fail-open이었다** — 미지원 브라우저가 규칙을 통째로 버리면 게임 화면
   BGM이 `top:12`에 남아 배너·토글에 정면으로 들어간다. `body.no-scroll`로 바꾼 것이 옳다
   (같은 파일 :383-385에 «`:not()`은 forgiving이 아니라 폴백이 안전하다»고 따진 전례가 있다).
